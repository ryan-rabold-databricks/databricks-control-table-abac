Attribute-Based Access Control · Reference Architecture

One control table drives every policy

A working framework where governance teams declare access in a table and tag columns — and native Unity Catalog ABAC policies are generated, applied, and audited from that single source of truth. Built and verified live.

The reframe that makes it work

The instinct is "a control table the query engine reads to decide access." That isn't buildable — a UC filter/mask function is SQL, it can't take a table name at runtime, and it never receives the matched tag value. So the control table is the source of truth a generator renders native policies from at deploy time. The only thing read at query time is the flat mapping table — one row per grant. Everything stays a real, auditable UC policy.

03

Consolidation, measured

A naive approach runs a separate function per row-filter policy. Here every attribute-based row filter is the same function; new attributes are data, not code.

Row filters

N filters → 2 functions

Every row filter binds rls_scope_filter (1 attr) or rls_scope_filter2 (OR). New attributes are data, not code — add service_line the same way.

Column masks

N columns → 1 function

mask_value_any covers every tagged column. A new masked field is one tag, zero new policies.

05

Adding a policy

New row-filter attribute

  1. Add the value to the governed tag (tag-policies API).
  2. Insert one row into policy_control.
  3. Tag the column: SET TAGS ('row_filter_policy'='…').
  4. Run apply_policies.py.
  5. Grant users, groups, or service principals with inserts into rls_principal_grants.

New masked column

  1. Tag it: SET TAGS ('masking_rule'='redact').

Retire a policy

  1. Set enabled=false.
  2. Run the generator — it drops the policy and touches nothing it doesn't manage.
06

Runtime constraints found — read before rollout

At most one row filter per table

This runtime throws UC_ABAC_MULTIPLE_ROW_FILTERS. It contradicts a common assumption (roadmap #11: self ∩ service-line ∩ location as three stacked filters). Multiple attributes on one table must be combined into a single function — which is why rls_scope_filter2 exists (and rls_encounter uses it for department OR provider). Verify against your workspace version.

Policies require governed tags

A policy condition only accepts a tag key registered via the Tag Policy API, with the value in its allowed set. Plain column tags fail; any trigger tag must be registered as a governed tag.

A function can't receive the matched tag value

The attribute type is passed as a literal — USING COLUMNS ('department_id', col). Validated working; it's what lets one generic function serve every attribute.
